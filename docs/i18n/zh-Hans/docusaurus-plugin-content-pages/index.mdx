<dfk-features section-title="它给 DuckDB 加了什么">

<dfk-feature icon="lucide:braces" title="就是普通的 SQL 函数">
九个名字、二十一个签名，全是标量函数。放进投影里、放进 WHERE 里，和 DuckDB 自带的函数一起用。
</dfk-feature>

<dfk-feature icon="lucide:file-output" title="接的是内容，不只是路径">
查询产出的东西大多还没有文件。op_write_file 把它写出去、返回路径，op_open_content 在同一次调用里顺手打开，op_open_html 连选项都不用写。
</dfk-feature>

<dfk-feature icon="lucide:spell-check" title="文件名来自数据本身">
报表标题、客户名当不了文件名。op_sanitize_filename 把它改写成各平台都认的名字，op_sanitize_filename_check 只回答它本来是不是这样一个名字 —— 于是查询能数出哪些会被改动，而在这层一条都不动。
</dfk-feature>

<dfk-feature icon="lucide:package" title="包装的是两个成熟库">
启动那件事是 open 这个库的，文件名的规则是 sanitize-filename 的。这里是把它们接到 SQL 上，而不是各重写一遍，所以一次调用的行为和库本身一致。
</dfk-feature>

<dfk-feature icon="lucide:monitor-down" title="Windows、Linux 与 macOS">
每个版本按桌面平台各挂一份 .duckdb_extension，可以直接按 URL 加载。没有 WebAssembly 构建 —— 启动器要的是一台有人的桌面，这正是这个扩展的定位：交互式查询，而不是嵌进应用里的 DuckDB。
</dfk-feature>

<dfk-feature icon="lucide:shield-check" title="DuckDB 1.4 或更新">
基于 DuckDB 的 C 扩展 API 构建，一个二进制就能加载进 DuckDB 1.4 及之后的版本，不需要重新编译。
</dfk-feature>

</dfk-features>

## 装一次，之后就在 SQL 里调用

调用处不用 import 任何东西。左边装一次，右边就能在任何能写 DuckDB 函数的地方用它。

<div className={styles.codeGrid}>

```sql title="duckdb"
-- once per installation, then once per session
INSTALL duckfn_open FROM community;
LOAD duckfn_open;
```

<div className={styles.codeColumn}>

```sql title="duckdb"
SELECT op_write_file(markdown, 'md');  -- content out to a file, its path back, nothing started
SELECT op_open_html('<h1>hello</h1>');  -- a temporary .html, opened in the default browser
SELECT op_sanitize_filename(report_title, '_');  -- a string in, a name every platform accepts out
SELECT op_open_path('report.html');  -- true once a launcher has been started
SELECT op_open_commands('report.html');
-- VARCHAR[]: the launch commands op_open_path would try on this machine, in order
```

后面那些注释就是每次调用的答复：前两个递进去的是一个还没有文件的值，后两个是已经存在的路径 —— 最后一行只列出真去启动时会依次尝试的命令，一条都不尝试。中间那个停在字符串里：op_sanitize_filename 改写的只是文件名，既不碰磁盘，也不碰桌面。
