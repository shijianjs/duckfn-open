<dfk-features section-title="What it adds to DuckDB">

<dfk-feature icon="lucide:braces" title="Ordinary SQL functions">
Nine names and twenty-one signatures, every one of them scalar. Call them in a projection or a WHERE clause, next to DuckDB's own functions.
</dfk-feature>

<dfk-feature icon="lucide:file-output" title="Content, not only paths">
Most of what a query produces has no file yet. op_write_file writes it out and returns the path, op_open_content opens it in the same call, op_open_html needs no options at all.
</dfk-feature>

<dfk-feature icon="lucide:spell-check" title="File names from your data">
A report title or a customer name is not a file name. op_sanitize_filename rewrites one into a name every platform accepts, and op_sanitize_filename_check answers whether it already is one — a query can count what would change without changing it.
</dfk-feature>

<dfk-feature icon="lucide:package" title="Two crates, wrapped">
The launching is the open crate's job and the file-name rules are sanitize-filename's. This extension wires both to SQL rather than reimplementing them, so a call behaves the way the crate does.
</dfk-feature>

<dfk-feature icon="lucide:monitor-down" title="Windows, Linux and macOS">
Each release carries one .duckdb_extension per desktop platform, loadable straight from its URL. There is no WebAssembly build — a launcher needs a desktop with someone at it, which is the situation this extension is for: interactive queries, not DuckDB embedded in an application.
</dfk-feature>

<dfk-feature icon="lucide:shield-check" title="DuckDB 1.4 or newer">
Built against DuckDB's C extension API, so one binary loads into DuckDB 1.4 and later without a recompile.
</dfk-feature>

</dfk-features>

## Install once, then call it from SQL

There is nothing to import at the call site. Install the extension once (left), then call the functions anywhere DuckDB takes a function (right).

<div className={styles.codeGrid}>

```sql title="duckdb"
-- once per installation, then once per session
INSTALL duckfn_open FROM community;
LOAD duckfn_open;
```

<div className={styles.codeColumn}>

```sql title="duckdb"
SELECT op_write_file(markdown, 'md');  -- content out to a file, its path back, nothing started
SELECT op_open_html('<h1>hello</h1>');  -- a temporary .html, opened in the default browser
SELECT op_sanitize_filename(report_title, '_');  -- a string in, a name every platform accepts out
SELECT op_open_path('report.html');  -- true once a launcher has been started
SELECT op_open_commands('report.html');
-- VARCHAR[]: the launch commands op_open_path would try on this machine, in order
```

Those trailing comments are the answers. The first two calls take a value that has no file yet, the last two a path that already exists — and the final one only lists the commands a launch would try, without trying any of them. In between, op_sanitize_filename is the one that stays a string: it rewrites a file name, touching neither the disk nor the desktop.
